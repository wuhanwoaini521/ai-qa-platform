# Quality Gates — 统一质量门与判定规范

Status: `[CURRENT]` · Effective: 2026-10-29 · Applies to all agents (Claude Code / Pi / Codex / human reviewers)

本文定义本项目「一个检查算什么状态」与「一次交付算什么结论」的统一口径。
它不新增产品需求，也不放宽任何约束；与 `docs/ROADMAP.md` §0 冲突时以 §0 为准。

来源说明：本文由研究分支 `research/autonomous-rd-2026-10-28` 的 `.pi/team/QUALITY_GATES.md`
（提交 `645bc20`）裁剪而来，只保留与工具无关、可在当前 `main` 执行的部分。
Pi 专属内容（`.pi/settings.json`、`pi-subagents`、`agent-browser` 会话、特定任务的 Graphite 路径）未复制。

---

## 1. 判定权归属

1. **产品测试判定只来自真实执行结果**：Pytest 退出码是测试 PASS/FAIL 的权威来源。
   AI 可以分类、解释、总结和建议，**不得覆盖、放宽或重新解释**判定结果。
2. **代码变更需人工批准**：AI 修复流程止于 proposal + diff；人工批准后才应用，并做精确验证。
3. **确定性优先**：测试选择、门禁、覆盖率由已记录的执行数据计算，不由模型判断。
4. **外部写入先预览**：Jira / TestRail / GitHub / Jenkins 等写入必须先展示预览并显式确认。
5. **无无人值守循环**：自动化必须有界、可审查、可回滚。
6. **单一所有权**：不新增第二套 Runtime / Agent / Provider；`BrowserRuntime` 是唯一 Playwright
   生命周期所有者；Task Runtime 是注册任务的调度所有者。

## 2. 词汇表

### 2.1 单项检查状态（gate status）

每项检查只能取以下值之一，且必须附证据。

| 状态 | 定义 | 必要证据 | 不代表 |
|---|---|---|---|
| `PASS` | 检查已执行，结果符合预期 | 命令、环境与版本、退出码 0、耗时、证据路径或计数 | 不代表其它未跑的检查也通过 |
| `FAIL` | 检查已执行，结果不符合预期 | 同上 + 失败输出、复现步骤或失败用例 id | 不代表整个产品不可用 |
| `BLOCKED` | 已按 §4 做过有界环境尝试，仍无法执行 | 尝试过的命令/方案、失败原因、缺失的前置条件 | **不等于通过**，也不等于产品缺陷 |
| `UNKNOWN` | 未执行，或结果无法解释 | 未执行原因（未尝试 / 结论不确定） | **不等于通过**；必须在交付前解决或显式接受 |
| `N/A` | 该项目不存在此能力（不是「没有环境」） | 说明为何不适用 | 不得用于回避可执行的检查 |

历史文档中的 `SKIP` / `NOT TESTED` 统一映射为 `UNKNOWN`；
「有环境但缺依赖」映射为 `BLOCKED`；「项目根本没有该能力」才是 `N/A`。

### 2.2 交付结论（deliverable verdict）

一次代码交付 / 修复 / 重构任务，最终结论只能是：

| 结论 | 条件 |
|---|---|
| `PASS` | 请求范围内的必需门全部执行并通过；无未解决的 P0，无涉及正确性/安全/兼容性/回归的 P1 |
| `PARTIAL` | 主要证据为正面，但存在未执行、`BLOCKED` 或 `UNKNOWN` 的必需门，或只剩非阻断问题；必须逐条列出未验证项 |
| `FAIL` | 已执行的门显示产品缺陷；核心路径不可用；存在未解决的 P0/P1；必要的回归仍失败 |

`PARTIAL` 与 `FAIL` 的区别是**「没验证到」还是「验证出问题」**。
`BLOCKED` / `UNKNOWN` 的必需门出现时，交付结论**不得为 `PASS`**。

### 2.3 就绪结论（readiness verdict）

架构评审、发布候选、多实例/生产就绪等非单次交付的评估，可使用：

`PASS` / `PARTIAL` / `FAIL` / `BLOCKED`

`BLOCKED` 表示关键通道无法验证（例如无隔离 PostgreSQL 16 或多进程环境），
此时不得声称该维度通过。`UNKNOWN` 不作为就绪结论，必须降级为 `PARTIAL` 或 `BLOCKED`。

### 2.4 与现有 Skill 的关系（避免口径冲突）

- `.agents/skills/project-delivery` 与 `full-project-validation` 要求最终结论为 `PASS` / `PARTIAL` / `FAIL`。
  本文**兼容**该约束：交付类任务仍只输出这三者；`BLOCKED` / `UNKNOWN` 只作为单项检查状态存在，
  并在最终结论中体现为 `PARTIAL`（附具体未验证项）。
- 只有当任务本身是「通道就绪评估」（§2.3）时，才允许把 `BLOCKED` 作为总体结论。

## 3. 证据标准

任何被声称完成的检查，必须同时提供：

1. **精确命令**（可直接复制复跑，不用「跑过测试」这类概述）。
2. **环境**：OS、Python/Node 版本、数据库类型与版本、单进程或多进程；UI 检查还需视口尺寸。
3. **结果**：退出码、通过/失败/跳过计数、耗时。
4. **证据路径**：日志、截图、报告或数据库快照位置；不得只存在于聊天记录。
5. **绑定版本**：提交 SHA 或工作区状态（有未提交改动时必须说明）。

未满足以上任一项的结论，按 `UNKNOWN` 处理。

---

## 4. 环境不可用时：先尝试，再 BLOCKED

判定 `BLOCKED` 前必须完成有界尝试：

- 检查项目自带 harness、脚本与已有 fixture（如 `apps/api/tests/conftest.py`）。
- 在任务授权范围内，可用一次性、固定版本、仅 loopback 的临时资源（本机已可用 Docker 时优先使用）。
- PostgreSQL 验证：库名必须含 `test`，只绑定 `127.0.0.1`，用完停止并清理；不得指向共享或生产库。
- 禁止：`sudo`、修改系统级配置、安装系统服务、修改依赖锁文件。
- 记录：实例版本、启动命令、隔离方式、测试命令、退出码、清理步骤。

完成以上仍不可行，才记 `BLOCKED`，并写明缺什么才能解阻。

## 5. 门目录

### 5.1 仓库与静态检查

- `uv run ruff check .`、`uv run ruff format --check .`、`git diff --check`。
- OpenAPI 契约：`uv run python scripts/export_openapi.py --check`。
- 适用范围：任何 Python / 契约改动。

### 5.2 后端与 API

- 定向 Pytest → 相关集成测试；鉴权与越权负向用例；错误路径；持久化与事务一致性。
- 必须复用现有服务与仓储；不得为让测试通过而放宽语义或伪造成功。

### 5.3 前端与浏览器

- `pnpm --filter @ai-qa/web test`、`typecheck`、`lint`、`build`；改动文案时加 `i18n` 检查。
- 桌面优先，验收视口：**1280×800、1440×900、1920×1080**；不主动扩展手机端范围。
- 真实浏览器交互必须与截图证据分开记录；截图只能证明渲染状态，不能证明交互可用。
- 浏览器不可用时记 `BLOCKED`/`UNKNOWN`，不得以源码阅读替代真实 UI 验收。

### 5.4 运行时与异步任务

- 验证真实状态迁移、超时、取消、重试/恢复、资源清理、SSE/事件真实性。
- 必须使用一次性隔离数据库或 fixture；伪造 run 不能作为真实执行证据。
- 恢复类改动必须测试：状态竞争、迟到写入、失败注入回滚、终态不可回退。

### 5.5 数据库与恢复

- SQLite 与 PostgreSQL 视为两个通道，行为差异是平台缺陷，不是测试环境差异。
- 生产声明必须基于 **PostgreSQL 16**；其它版本（如 18.6）只能作为该版本的证据，不能替代。
- 单进程验证不能替代多实例 / 多进程所有权验证；缺少时明确记为 `BLOCKED`。
- 状态与事件写入必须事务一致，或有确定性修复路径。

### 5.6 AI 与决策边界

- 必须使用真实失败上下文与真实 provider；任何 mock / 离线结果要显式标注，不能算 provider 成功路径。
- 分析与提案分离；patch 预览 / diff 在前，人工批准后才应用；批准后做精确用例验证。
- AI 结论是建议层，不写入确定性判定字段，不覆盖覆盖率、flaky 分或测试结论。

### 5.7 研究与来源证据

- 固定官方 release/tag、许可证文件与 manifest；引用 URL 与核实日期。
- 来源元数据、运行时兼容性、本项目实测结果三者分开陈述。
- 未安装、未运行的候选技术不得描述为「已验证可用」；未知是合法结论。
- 未经授权不安装候选、不调用付费 provider、不推荐生产采用。
- 研究资产当前位于 `research/autonomous-rd-2026-10-28`，读取方式见 `CLAUDE.md`。

### 5.8 评审与集成

- 独立评审必须使用不同上下文，输入为原始任务 + 验收标准 + 实际 diff + 执行结果。
- `P0` 阻断验收；未解决的正确性/安全/兼容性/回归 `P1` 同样阻断 `PASS`。
- 评审确认改动范围、无调试残留与密钥、无越权提交；保留既有未提交修改。

### 5.9 外部写入与发布前检查

- 推送 / PR / 外部系统写入前：检查精确 staged diff、未跟踪文件、密钥与数据、测试证据、
  分支与上游关系、目标可见性、影响与回滚方式，并展示预览。
- 禁止强制推送、自动合并、自动部署；发布动作需单独人工授权。

---

## 6. 报告格式（最小要求）

任何验收报告至少包含：

1. 绑定版本（SHA / 工作区状态）与环境。
2. 检查矩阵：项目 → 状态 → 证据。
3. 明确列出的未验证项与残余风险。
4. 结论：按 §2.2 或 §2.3 选择一个，并说明理由。

禁止只给结论不给证据，也禁止用「全部通过」替代未执行项的列举。
