## Focus comparisons

### Browser Use autonomous exploration

The current product already has bounded browser exploration and task execution in `TaskBrowserExecutor`, plus project Discovery in `QualityDiscoveryService`; both use the existing `BrowserRuntime` and decision/provider paths. An autonomous library may improve page reasoning, but it also introduces a second planner, safety policy, retries, state, and evidence contract if wired directly. The isolated same-site baseline currently proves only the existing Playwright path. Browser Use itself was **not installed or run**, so no claim is made about comparative success, locator stability, recovery, time, or tokens.

### Skyvern act / extract / validate

A staged act/extract/validate contract is a useful design lens: every action should cite observations, every extraction should be evidence-backed, and validation should be deterministic when it is a test assertion. The platform has corresponding capabilities across `TaskBrowserExecutor`, `QualityDiscoveryExecutionMixin`, and Pytest, but not one shared browser-action lifecycle contract. This does **not** justify adding Skyvern: deployment, license, BrowserRuntime ownership, auth/data boundaries, custom provider, and reproducible browser behavior remain unverified.

### LangGraph persistence, recovery, approvals

The existing Task Runtime already persists plans, steps, state, evidence, decisions, and cursor events; it supports approval, pause/resume, retry/replan and conservative restart recovery. The remaining question is whether a particular durability/fanout requirement is not economically achievable within that runtime. A framework checkpoint would not itself make Playwright sessions, Pytest subprocesses, workspace writes, and database transactions atomic. Compare against current contracts first; do not adopt a second graph scheduler by default.

### CrewAI roles

Role-based multi-agent collaboration is not a substitute for persisted task state, idempotency, deterministic execution, permission checks or human authorization. Project workflows are currently fixed registered tools and plans, which is more reproducible than allowing agents to invent a graph. Multi-agent work remains an experiment only if a quantified quality gain exceeds token, latency, security and debugging costs.

### Dify / n8n visual orchestration

The current “Workflow Canvas” is an execution DAG/trace projection (`RuntimeFlow`), not a general workflow editor. Dify/n8n could supply a separate authoring interface but would add another service, identity, persistence, retries, secrets and API boundary. There is no evidence that a second workflow system is needed. Reuse current React studio and persisted task model; borrow observability/authoring ideas only after UX/product evidence.
