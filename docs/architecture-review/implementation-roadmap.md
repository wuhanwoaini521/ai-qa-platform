## Sequencing constraints

- Phase 1 output is a schema/API contract, not a second event store. No destructive `ALTER/DROP` until migration parity and a deprecation window pass.
- Phase 2 should precede automated retry/resume or framework checkpoint adoption; otherwise retries may duplicate browser, file, test, or integration side effects.
- Phase 3 and 4 stay within current `BrowserRuntime` / `TaskRuntimeService` boundaries.
- Phase 5 is the first user-visible capability closure. It needs actual operator approval in the live UI; a test client submitting `approved=true` is not acceptance of the user approval experience.
- Phase 6 UI work is gated on stable contracts, not used to mask missing backend state.
- Phases 7–8 depend on measured needs and security/legal approval; they may be skipped or split if evidence shows no need.
- Each phase maintains its own migration and rollback note; no automatic merge, commit, deploy, or release.
