# Operating Model

## Authority and boundaries

- **Engineering Director / Orchestrator (parent Pi):** owns intake, role selection, task DAG, scope, approval checks, integration, final evidence-based acceptance, and user handoff. It is not allowed to manufacture child-agent results.
- **User:** retains final authority over significant product direction, scope expansion, production actions, commits/pushes/merges/deploys, external writes, and code changes not explicitly authorized by the request.
- **AI / test verdicts:** test PASS/FAIL comes only from actual deterministic test execution/exit status. AI cannot override it. AI repair remains proposal → preview/diff → human approval → exact verification.
- **System boundaries:** reuse existing `DecisionService`, Task Runtime, `BrowserRuntime`, repository boundaries, provider registry, RBAC, and data persistence. Never create a second Runtime, Agent, or Provider layer.
- **Worktree:** inspect current HEAD/status before acting; preserve all existing staged, unstaged, and untracked work. No automatic stash, reset, clean, commit, push, merge, or production deployment.
- **Desktop First / Graphite:** only desktop viewports 1280×800, 1440×900, and 1920×1080 are in scope. The approved Graphite Developer Studio is the visual baseline for Dashboard and Workspace Debug/Explore. The user-authorized fidelity task `.ai-runs/2026-10-27-graphite-fidelity-recovery/00-request.md` extends this direction, for that task, to Projects, Requirements, Test Explorer, Write Tests, Results, AI Repair, and Quality. For those added surfaces, reuse their existing React content/actions and the existing Graphite tokens; do not invent page IA. This is a scoped override, not blanket approval for unrelated routes. Old mobile guidance is OUT OF SCOPE under root `AGENTS.md`.

## Role contracts

Tool-independent role definitions and authority are in [`engineering-knowledge/team-definition.md`](../../engineering-knowledge/team-definition.md); this file defines the Pi adapter and project-specific delivery gates. Each child receives a bounded brief with goal, current repository/ref, user-approved scope, exact file/behavior ownership, acceptance criteria, evidence, validation command, and stop/escalation condition. Every result states completed work, files read/changed, actual tests/evidence, risks, blockers, and next step.

## Task lifecycle

`BACKLOG → READY → IN_PROGRESS → IN_REVIEW → IN_QA → DONE`, with `BLOCKED` or `REJECTED` when evidence/authorization requires it.

1. **Intake:** classify Product Feature, UX Improvement, Bug Fix, Refactor, Technical Debt, Performance, Security, or Test Infrastructure. Preserve user wording and separate goal from solution.
2. **Planning:** Product Manager defines value/scope/criteria; Architect checks contracts/runtime/data impact; Design Director joins for UI. Orchestrator assigns a small DAG and unique file ownership.
3. **Design / Contract:** inspect existing source before creating anything; define UX flow, API schema, data ownership/state lifecycle, and existing service reuse. Write an ADR only for a material architecture choice.
4. **Implementation:** one authorized writer per file/worktree; parallel work is only for independent seams. Default max 3 concurrent children; use bounded foreground work, no detached sessions. Mission limits: at most 2 formal debate rounds, 3 implementation/review/fix rounds per task, and an explicit timeout/stop condition for each PoC.
5. **Review:** fresh independent `reviewer` context; compare task, acceptance, actual diff, and tests. Fix Blocker/Major and correctness/security/compatibility P1 before moving on. Max 3 implementation→review→repair rounds.
6. **QA:** independent QA executes applicable checks and real browser/API/runtime interactions. Record exact command, environment, exit status, evidence paths and untested areas. No mock or screenshot can stand in for a real runtime/provider.
7. **Acceptance:** functional/engineering and visual/product quality are separate gates. Use `PASS`, `PARTIAL`, `FAIL`, or `BLOCKED` only against recorded criteria/evidence; no passing criterion can be inferred from code compilation alone.
8. **Environment fallback:** when an environment-dependent check is unavailable, inspect the project harness and local/container options first. If the current task authorizes temporary provisioning, use isolated, pinned, loopback-only resources under temporary paths; do not use `sudo`, change global/system configuration, or point destructive schema-reset tests at shared data. Record setup, version, tests and cleanup. Mark BLOCKED only after the bounded authorized options are unavailable or fail.
9. **Handoff:** update Backlog and existing `docs/agent-handoff.md` at verifiable milestones with current commit, changed scope, real test evidence, blockers, residual risks, and next command.

Read-only requests do not create `.ai-runs` logs. Authorized multi-stage deliveries maintain concise run evidence. No task starts automatically after this pilot; the next-stage tasks await user selection.

## Delegation and recovery

- Real subagent delegation is available only when the current Pi process exposes the `subagent` runtime (or `subagents_enable`). Start with fresh context for independent review. For a normal direct child, pass `async:false` as an actual tool-call parameter and `options:{context:"fresh"}`; do not merely mention `async:false` in task text. Project settings disable async-by-default, auto-resume, missions, schedules, and workflow scripts, so do not send mission/workflow/schedule arguments.
- Never use schedules, background jobs, recursive agents, or unattended loops. Do not dispatch two writers to the same file/worktree. Maximum 3 concurrent children, but use less when context, memory, model or isolation makes it safer. Formal debate is capped at 2 rounds; automatic repair is capped at 3 rounds, then the task is BLOCKED.
- If the extension/runtime is absent, unavailable, or fails, report the exact observed limitation and run clearly labeled serial role steps. A simulated conversation is never evidence of delegation.
- Children do not spawn children unless the parent explicitly planned and bounded that fanout. Child output is advisory until the parent verifies it and integrates it.
- On interruption, resume from `docs/agent-handoff.md`, current Git status, the task backlog/evidence, and actual test results. Pi does not continue developing after its process exits.
