# RC Hotfix 1 — task cancel fencing (R18-B2)

Base: HEAD `6e2705b`, tag `rc-2026.10.22` (left untouched). New tag on the hotfix commit: `rc-2026.10.22-hotfix1`.
Scope: one defect (B2). No feature work, no refactor of TaskRuntime, no second scheduler.

## 1. What was wrong

| Path | Before | Why it breaks ownership |
| --- | --- | --- |
| `apps/api/app/services/task_command_service.py:380 cancel()` | unconditional `update_task(status=CANCELLED)` | any authorized caller wrote the terminal state, including a replica that owned nothing |
| `apps/api/app/services/task_execution_orchestrator.py:481 _finish()` | wrote the terminal row directly when `current_lease()` was `None` | a caller with no lease context bypassed the fence |
| `apps/api/app/services/task_scheduler_service.py:100 recover_interrupted()` | `unfinished_stale()` then unconditional `update_task(BLOCKED)` | select-then-write race against a live owner |
| `_execute_step` wait loop | only reacted to `status == CANCELLED` | a recorded request was invisible to the owner until a step happened to end |

Reproduced on the dev machine, not in theory: cancel recorded `cancel_requested_at`, the task stayed `RUNNING`
for ~60 s and then its status was overwritten with `BLOCKED`. Root cause: a second, orphaned API process
(uvicorn from 20:43 the previous day, parent dead, still holding `runtime/ai_qa_platform.db` and a scheduler
running the old code) was the real executor. The HTTP replica wrote a terminal state it did not own; the owner
later wrote its own. That is exactly B2.

## 2. The fix

- `0022_task_cancel_request`: `agent_tasks.cancel_requested_at`, `cancel_requested_by` (reversible batch alter).
- `TaskRepository.request_cancel(task_id, actor)` — single conditional UPDATE, first request wins, terminal rows
  untouched, never writes a status.
- `TaskRepository.finish_fenced(...)` — single conditional UPDATE guarded by `status not in TERMINAL` plus either
  `lease_owner + lease_token` match or `require_no_live_lease`; returns `rowcount == 1`.
- `TaskCommandService.cancel()` — record the request (`task.cancel_requested`), then `finish_fenced` **only** when
  nobody holds a live lease. Otherwise it returns the request state and lets the owner finish.
- `_finish()` — always fenced; a fenced write that loses records `task.lease_lost`.
- Owner reaction: DAG loop head, step boundary (`TaskCancelled`), and heartbeat (every 20 s cancels its own
  execution task). `except asyncio.CancelledError` finishes `CANCELLED` only when a request exists, so a process
  shutdown still leaves recovery to the startup path.
- Cancel wins over failure: a `FAILED`/`BLOCKED` terminal write that races a request becomes `CANCELLED`, with the
  original outcome in `verification.interrupted_outcome`.
- Recovery: `recover_interrupted()` uses `finish_fenced(require_no_live_lease=True)` and turns a requested cancel
  into `CANCELLED` (`task.cancelled {via: "recovery"}`), an unrequested orphan into `BLOCKED`.
- UI: `RuntimeTaskActions` shows "取消已请求，任务会在当前步骤结束时停止。" and disables the button; `Task` /
  `AgentTask` types and the OpenAPI contract carry the new fields.

## 4. Honest limits

- **No second host.** The request/finalization split is proven in-process, on PostgreSQL with two sessions, and
  by a real field incident where a stale second process did clobber a cancel — but `MULTI_INSTANCE_PASS` stays
  BLOCKED.
- The dev machine had a stale process holding the database. Any acceptance run must first confirm that only one
  process holds `runtime/ai_qa_platform.db`; the script now fails loudly instead of passing silently.
- B1 (no DAG execution route) and B3 (remote CI / cross-host deploy) are untouched.

Verdict: **B2 PARTIAL** — mechanism fixed and verified on one host; release level unchanged.
