# Requirements Analysis

把一句话需求变成"能指导实现、能判定验收"的描述。目标不是写 PRD，而是消除歧义并确认改动边界。

## 六个必答问题

1. **User goal**：用户真正想得到什么结果？（不是"改哪个文件"，是"改完之后用户能做什么"）
2. **Acceptance criteria**：什么条件成立就算完成？必须可判定真假。
3. **Constraints**：不能碰什么？（兼容性、性能、依赖、发布约束、明确不做的事）
4. **Impact**：哪些模块和调用方受影响？改动触及行为、架构、数据、安全、用户界面或回归面的哪些部分？是否已有实现可以扩展？
5. **Compatibility requirements**：旧行为、旧调用方、旧数据格式是否必须继续可用？
6. **Unknowns**：还有哪些不确定？每一项要么去仓库里查证，要么变成明确问题。

## 规模纪律

用户一句话**不要**被扩写成大型 PRD。

- 需求规模应该匹配任务规模：`01-analysis.md` 写 15 行就够的任务，不要写成 15 页。
- 只有当任务确实是大型任务时，才展开多角色视角、边界清单、迁移方案。
- 不确定的点不要用想象补齐；能查就去查，查不到再记为未知。

## 验收标准写法

坏：

```text
搜索体验更好
分页没问题
UI 更清爽
```

好：

```text
输入关键词后 300ms 内出现结果；无结果显示空态文案；结果为空时 URL 不变化
翻到第 3 页再删掉第 1 页的一条数据，页码与总数不出现错乱
列表在 360px / 768px / 1440px 三个宽度下不出现横向滚动或文字截断
```

验收标准必须满足：

- 可观测：能通过测试、命令、截图或明确的输出判断真假。
- 与改动直接相关：不写"代码质量良好"这种无法验证的条目。
- 覆盖失败路径：至少一条涉及异常、空态或边界。
- 覆盖用户可观察结果与关键兼容性要求；不要把"测试通过"本身当作功能验收标准。

## 澄清纪律

先自行推断，再考虑提问。

应该自己推断（不要问用户）：

- 用哪个测试命令、lint 配置在哪、目录结构怎么组织。
- 某个函数被谁调用、现有测试覆盖到哪。
- 项目里是否已有同类实现可以参照。

才值得问用户：

- 存在两种以上都合理、且会导致返工的方案分叉（例如下沉到后端还是前端做筛选）。
- 需求与现有约束冲突（要求"不能改 API"但新功能必须改）。
- 破坏性变更、需要外部凭据、或会删除用户现有数据。

禁止问："要不要继续"、"要不要我测试一下"、"要不要做 review"。这些由流程自己判断。

## 记录位置

授权的交付任务将结论写入 `01-analysis.md`：当前架构、相关文件、证据、影响面、约束、风险和待验证假设。只读请求在回复中给出分析，不创建日志或计划文件。

**不写**模型内部思考过程、hidden reasoning、逐 token 推理。只写观察、决策、证据与未知。
